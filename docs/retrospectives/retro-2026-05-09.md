# Blob Todo M0-M3 開發回顧 (Retrospective)

**日期**: 2026-05-09
**專案範圍**: Blob Todo (從基礎骨架 M0 到 Chrome Extension 封裝 M3)
**參與角色**: AI Agent, User

## 1. 時間線與里程碑 (Timeline)

1. **M0 基礎骨架**: 快速建立 HTML 結構與 EventBus，分離關注點。
2. **M1 MVP**: 
   - 實作 TaskStore 與 LocalStorage 儲存。
   - 實作 LayoutEngine（排斥力碰撞演算）與 BlobRenderer。
   - 透過純 DOM 元素與 CSS `border-radius` 百分比，成功模擬出有機流體泡泡，而不需要引入 Canvas API 或 WebGL，大幅降低開發與維護成本。
3. **M2 UI 優化與功能完整化**: 
   - 將視覺從「科技暗色系」重構為「現代清新亮/暗雙棲」。
   - 移除多餘的裝飾與按鈕，並加入子任務進入/返回。
   - **問題發生**: 縮放視窗時，`ResizeObserver` 觸發過快導致 CSS `transition` 卡頓；且小視窗時 LayoutEngine 因物理邊界限制造成泡泡強制重疊。
   - **問題解決**: 導入 Debounce (防抖) 100ms；在 LayoutEngine 中加入面積偵測的自動縮放比例 (Squeeze Effect)。
4. **M3 Chrome Extension 打包**:
   - 分離 `index.html` 內聯樣式與腳本以符合 Manifest V3 CSP 規範。
   - 將 `TaskStore` 重構為非同步架構，優先適配 `chrome.storage.local`，並保留 fallback。

## 2. 順利的地方 (Worked Well)

- **使用 DOM + CSS 達成有機流體視覺**：起初可能會想要用 Canvas API 畫圓，但直接用 `div` + `box-shadow` + 複雜 `border-radius` 不僅效能好，而且所有點擊事件、Hover、甚至是字體排版都可以直接依賴原生 HTML 特性，省去自己寫碰撞檢測與事件委派的麻煩。
- **架構提早解耦 (EventBus + Store)**：透過 EventBus 傳遞 `tasks:changed`，讓 UI 渲染層與資料層完全脫鉤，後續要把 `localStorage` 換成 `chrome.storage.local` 時只需要改 TaskStore，Renderer 完全不受影響。
- **漸進式實作 (Thin Vertical Slices)**：先把功能做進單一 `index.html`，驗證物理引擎與操作手感後，最後 (M3) 才把 CSS/JS 抽離並加入 Extension API。這避開了開發初期繁瑣的環境設定與除錯成本。

## 3. 摩擦與挑戰 (Friction)

- **CSS 動畫與 JS 演算的衝突**：泡泡位移是透過 JS 算出來的 `left` / `top`，再加上 CSS 的 `transition`。當 `ResizeObserver` 頻繁觸發時，這兩者發生了嚴重的爭搶（Thrashing），導致畫面不斷抖動。
- **物理邊界與擠壓重疊**：初步設計 LayoutEngine 時，只給定了「最小泡泡半徑」，沒有考慮到「如果螢幕太小，把這些泡泡全塞進去必定會超越面積極限」，導致物理引擎算出的排斥力抵銷不了硬性的邊界條件，最後強制重疊。

## 4. 根本模式 (Root Patterns)

- **邊界情境設計缺失**：在 SD (System Design) 階段，通常會記得定義 "Viewport Resize" 要重新計算位置，但很容易遺漏「如果 Viewport 小於物件總面積時的 Fallback 策略（允許滾動、等比縮小、或是隱藏）」。
- **事件風暴 (Event Storm) 缺乏預設防禦**：只要用到 `ResizeObserver` 或是 `scroll` 事件去驅動 DOM 結構變更，就必須「預設加上 Debounce 或 Throttle」，這不該是優化選項，而是必須的架構。

## 5. 具體改善行動 (Actionable Learnings)

- **[Action 1] 更新 UI / 前端實作的 Skill Checklist**：
  在 `frontend-ui-engineering` 或規格分析階段，凡是涉及 `ResizeObserver` 的任務，強制要求檢查是否已加入 Debounce / Throttle 機制。
- **[Action 2] 更新 Spec Analysis 邊界檢查**：
  在撰寫動態排版 (如 Masonry, 物理碰撞引擎) 的 SA 文件時，必須將「當可用面積小於內容物最小總面積極限時的處理方式」列為必填選項。
- **[Action 3] 保留 Fallback 測試模式**：
  這次在封裝 Extension 時保留了若找不到 `chrome.storage` 則退回 `localStorage` 的設計非常棒。這應該被記錄為後續所有 Extension 開發的標準模式，這大幅提升了本機除錯的靈活性。
